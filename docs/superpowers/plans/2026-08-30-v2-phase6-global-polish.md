# v2 Phase 6 — Global Polish Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Commit policy override:** stays fully uncommitted until the project owner explicitly says to commit. Implementers do **not** run `git commit` or `git add`. Task review diffs are generated by snapshotting target files before dispatch and diffing the snapshot against the post-task file (`diff -u`), not `git diff HEAD`.

**Goal:** The remaining site-wide texture from §14/§21 phase 6: a transition accent, a grain overlay, magnetic hover, and the pointer-reactive dot treatment deferred from Phase 2.

**Architecture:** Two tasks. Task 1 adds global, additive-only chrome (grain overlay, a brief transition accent) at the `App.jsx` shell level — nothing existing changes behavior, this only adds new always-present or route-keyed elements. Task 2 adds interactive polish to two already-shipped components (`NavRail`, `Hero`) — magnetic hover and a cursor-following glow — without altering their existing structure or animations.

**Two items from the original brief are explicitly dropped, not silently cut — both for the same reason: they risk fighting Phase 3's shared-layout glyph transition, which is the site's more significant, already-delivered feature.**

- **The "pixel-grid dissolve" full page-transition curtain (§14 #2, for route changes) is not built as a full opaque wipe.** Phase 3's Home→Details morph needs the page content visible and animating *throughout* the transition for the glyph to visibly travel between positions — a full-coverage curtain would hide exactly the moment that transition needs to be seen. Task 1 ships a much lower-risk version instead: a brief, low-opacity (max 15%) mosaic flicker that reads as a "static/glitch" texture accent without ever obscuring the page underneath.
- **The View Transitions API layer (§14 #3) is not added.** It works by having the browser snapshot the DOM before/after a navigation and cross-fade between the two snapshots natively — a second, independent animation system running at the same time as Motion's `AnimatePresence`/`layoutId` machinery from Phase 3 would very likely double-animate the same DOM change (the browser's own crossfade plus Motion's shared-layout morph, fighting each other for the same pixels). Coordinating the two correctly is a real, separate piece of engineering, not a small addition — it needs its own design pass, not a bullet point in a polish phase. Left as an explicit future decision in the spec (see the correction below), not attempted here.

## Global Constraints

- Only `var(--ink)`, `var(--paper)`, `var(--meta)`, `var(--signal)` colors — no new hardcoded hex/rgba.
- Everything in this phase must respect `prefers-reduced-motion` — the grain overlay is static (not animated) so it needs no reduced-motion branch; the transition flicker and magnetic/glow effects must fully disable under reduced motion (skip attaching the relevant handlers/animations entirely, not just shorten them).
- No new npm dependency — grain uses a plain inline SVG `feTurbulence` filter; magnetic/glow use `motion/react` (already a dependency) or plain CSS custom properties updated via a ref (no per-frame React state, to keep mousemove handling cheap).
- Do not modify Phase 3's `layoutId`/shared-layout logic in `App.jsx`, `Projects.jsx`, or `ProjectDetail.jsx` — this phase only *adds* elements alongside the existing transition system, never touches its timing or structure.

- [ ] **Step 2: Add the transition flicker component**

Add above the `PageTransition` function in `App.jsx`:

```jsx
function TransitionFlicker() {
  const location = useLocation();
  const reduceMotion = useReducedMotion();

  if (reduceMotion) return null;

  return (
    <motion.div
      key={location.pathname}
      className="transition-flicker"
      initial={{ opacity: 0 }}
      animate={{ opacity: [0, 0.15, 0] }}
      transition={{ duration: 0.3, times: [0, 0.4, 1], ease: 'linear' }}
    >
      {Array.from({ length: 24 }).map((_, i) => (
        <span key={i} />
      ))}
    </motion.div>
  );
}
```

Render it inside `AppShell`, right after the grain overlay div:

```jsx
      <TransitionFlicker />
```

(Keyed by `location.pathname`, so React remounts it — and replays its opacity keyframe animation — on every route change. It renders `null` outright under reduced motion, not just a shortened animation, since a flicker effect is inherently motion-only content.)

### Task 2: Magnetic hover + Hero pointer glow

**Files:**
- Modify: `src/components/NavRail.jsx`
- Modify: `src/components/NavRail.css`
- Modify: `src/pages/Hero/Hero.jsx`
- Modify: `src/pages/Hero/Hero.css`

**Interfaces:**
- Produces: a local `useMagnetic(strength)` hook defined directly in `NavRail.jsx` (single consumer — the rail dots; not extracted to a shared file per this project's established YAGNI pattern of not generalizing single-consumer utilities prematurely, same reasoning as Phase 3's inline `useScrambleReveal`).

- [ ] **Step 1: Add the magnetic hover hook to NavRail**

In `src/components/NavRail.jsx`, add above the `RailDot` function:

```jsx
function useMagnetic(strength, reduceMotion) {
  const ref = useRef(null);
  const x = useMotionValue(0);
  const y = useMotionValue(0);
  const springX = useSpring(x, { stiffness: 300, damping: 20 });
  const springY = useSpring(y, { stiffness: 300, damping: 20 });

  if (reduceMotion) {
    return { ref, style: {}, onMouseMove: undefined, onMouseLeave: undefined };
  }

  const onMouseMove = (e) => {
    const rect = ref.current.getBoundingClientRect();
    x.set((e.clientX - (rect.left + rect.width / 2)) * strength);
    y.set((e.clientY - (rect.top + rect.height / 2)) * strength);
  };

  const onMouseLeave = () => {
    x.set(0);
    y.set(0);
  };

  return { ref, style: { x: springX, y: springY }, onMouseMove, onMouseLeave };
}
```

Add `useMotionValue`, `useSpring` to the existing `motion/react` import (`NavRail.jsx:3`, currently `import { motion, AnimatePresence, useReducedMotion } from 'motion/react';`):

```jsx
import { motion, AnimatePresence, useReducedMotion, useMotionValue, useSpring } from 'motion/react';
```

- [ ] **Step 2: Apply it to each rail dot button**

In the `RailDot` function, wrap the button with the magnetic hook:

```jsx
function RailDot({ section, isActive, onNavigate, reduceMotion }) {
  const magnetic = useMagnetic(0.3, reduceMotion);

  return (
    <motion.button
      ref={magnetic.ref}
      type="button"
      className={`rail-dot-btn ${isActive ? 'is-active' : ''}`}
      aria-label={`${section.code}, ${section.label}`}
      aria-current={isActive ? 'true' : undefined}
      onClick={() => onNavigate(section.id)}
      onMouseMove={magnetic.onMouseMove}
      onMouseLeave={magnetic.onMouseLeave}
      style={magnetic.style}
    >
      <motion.span
        className={`rail-mark ${isActive ? 'is-filled' : 'is-hollow'}`}
        whileHover={reduceMotion ? undefined : { scale: 1.4 }}
        whileTap={reduceMotion ? undefined : { scale: 0.85 }}
        transition={springHover}
      />
      <span className="rail-label font-mono">{section.code}</span>
      <span className="rail-tooltip font-mono">{section.label}</span>
    </motion.button>
  );
}
```

(The button element changes from a plain `<button>` to `motion.button` so it can accept the `style={{ x, y }}` motion values — everything else about it, including the inner `whileHover`/`whileTap` scale on `rail-mark`, is unchanged and composes normally with the outer magnetic offset.)

- [ ] **Step 3: CSS — nothing new required**

`rail-dot-btn` already has no conflicting `transform` set directly (the scale animation lives on the inner `.rail-mark` span) — the outer button's `x`/`y` motion values apply cleanly via `transform: translate(...)` that Motion manages automatically. No CSS changes needed for this step; skip straight to verification once Steps 1–2 are in place.

- [ ] **Step 4: Add the pointer glow to Hero's background**

In `src/pages/Hero/Hero.jsx`, add a ref and a mousemove handler that mutates CSS custom properties directly (not React state, to avoid a re-render on every mouse pixel moved):

```jsx
  const bgRef = useRef(null);

  const handleBgMouseMove = reduceMotion
    ? undefined
    : (e) => {
        const rect = e.currentTarget.getBoundingClientRect();
        bgRef.current.style.setProperty('--mx', `${e.clientX - rect.left}px`);
        bgRef.current.style.setProperty('--my', `${e.clientY - rect.top}px`);
      };
```

(Add this inside the `Hero` function, alongside the existing `reduceMotion`/`liveText`/`nameChars` declarations.)

Change the root element to attach the handler and give the background layer its ref:

```jsx
    <div className="hero-page" id="hero" onMouseMove={handleBgMouseMove}>
      <div className="hero-bg-layer" ref={bgRef} />
```

- [ ] **Step 5: CSS for the glow**

In `src/pages/Hero/Hero.css`, add after the existing `.hero-bg-layer` rule:

```css
.hero-bg-layer {
  --mx: 50%;
  --my: 50%;
}

.hero-bg-layer::after {
  content: '';
  position: absolute;
  inset: 0;
  background-image: radial-gradient(rgba(247, 247, 242, 0.35) 1.5px, transparent 1.5px);
  background-size: 22px 22px;
  -webkit-mask-image: radial-gradient(circle 180px at var(--mx) var(--my), black, transparent);
  mask-image: radial-gradient(circle 180px at var(--mx) var(--my), black, transparent);
}
```

(This adds a second, brighter dot layer on top of the existing static one, visible only inside a 180px circle that follows the cursor via a CSS mask — the dots "light up" near the pointer without any per-dot JavaScript. `prefers-reduced-motion` doesn't need its own branch here: without `onMouseMove` attached, `--mx`/`--my` just stay at their default `50%, 50%` and the brighter patch sits static in the center, which is a harmless, non-distracting fallback rather than something that needs suppressing.)

Run `npm run build`. Run `npm run dev`. Confirm:
