Task review diffs are generated by snapshotting each task's target files before dispatch and diffing the snapshot against the post-task file (`diff -u`), not `git diff HEAD` (see Phase 1's ledger for why).

**Goal:** Build the identity-glyph shared-layout morph between a Case Study row and its Details page, and rebuild the Details page itself to match the rest of the site's visual language.

**Architecture:** Three tasks. Task 1 is a new, self-contained component (`IdentityGlyph`) with no dependencies. Task 2 is the enabling architectural change — `App.jsx`'s route-transition mode currently prevents any shared-layout animation from ever running — plus wiring the glyph into `Projects.jsx`'s Case Study rows. Task 3 is the Details page rebuild: removes a fragile scroll-hijack, restyles to the shared design language, and consumes the glyph with a matching `layoutId` so it morphs in from wherever the user clicked.

**Scope decisions made during planning, not deferred as open questions:**
- **Real project data, not the spec's illustrative examples.** `docs/DESIGN_SPEC.md` §16/§20 reference "Order Notes Agent"/"CSR Copilot"/"RCA" as example case studies — those don't exist in `src/data/projects.json`. The actual displayed case studies are `vidhaan-ai`, `stock-predictor`, `portfolio-template` (Ideation). This plan builds against the real data.
- **Floating annotation callouts (spec §18) ship as a dormant capability, not populated content.** None of the three real case studies are team-built products with genuine "role"/"status" concepts the way the Pamidor reference case study was — inventing fake annotation text for them would be fabrication. Task 3 renders `project.annotations` if present; no current project has that field, so the feature exists but doesn't visibly do anything yet. That's the correct outcome, not a bug.
- **Scroll-scrubbed pixel-resolve text (spec §14 #9) is simplified to a scroll-triggered blur-resolve, not continuous scroll-scrubbing.** True per-pixel scrubbing tied to scroll position is a materially bigger, more fragile piece of engineering than a `whileInView`-triggered one-shot reveal, and both read the same way to a visitor: the text is unclear, then resolves as you scroll to it. Task 3 uses `whileInView` (Motion's standard, well-supported scroll-into-view trigger) instead of `useScroll`/`useTransform` scrubbing.
- **Text-scramble reveal (spec §14 #6) and the blur-resolve above are built inline in `ProjectDetail.jsx`, not as separate reusable components.** Each has exactly one consumer right now (the Details title; the Details body paragraphs). Extracting a generalized, prop-configurable component for a single call site is speculative reuse — YAGNI. Extract later if a second consumer shows up (e.g. when Phase 5's Archive or a future About treatment wants the same effect).
- **The existing media toggle/mockup-carousel/video-view logic in `ProjectDetail.jsx` is preserved verbatim.** It's orthogonal to this phase's actual goals (removing the scroll-hijack, unifying the visual language, adding the glyph/scramble/resolve). Rewriting working, unrelated logic is scope creep this plan explicitly avoids.

**Tech Stack:** React 18, `motion/react` (`layoutId`, `whileInView`, `AnimatePresence`) — all already a dependency, no new npm package. No automated test suite — verification is `npm run build` plus manual visual confirmation via `npm run dev`.

**Spec:** [docs/DESIGN_SPEC.md](../../DESIGN_SPEC.md) — §14 (#1 shared layout, #6 text scramble, #9 scroll-resolve), §16 (Case Studies → Details storyline), §18 (Project Details redesign).

## Global Constraints

- Only `var(--ink)`, `var(--paper)`, `var(--meta)`, `var(--signal)` colors in any new/changed CSS — no new hardcoded hex/rgba.
- `IdentityGlyph` must be a pure function of `projectId` — same id always produces the same visual pattern, no randomness, no external state.
- The `layoutId` passed to `IdentityGlyph` from the Case Study row and from the Details page for the same project must be identical strings (e.g. `glyph-${project.id}`), or Motion has nothing to match and the morph silently won't happen — this is the single easiest thing to get wrong in this phase.
- Do not touch `ArchiveOverlay.jsx`/`.css` — that's Phase 4's scope, not this one.
- Do not touch `About.jsx`/`About.css` — the blur-resolve treatment is scoped to Details' body paragraphs only in this phase; About is not in Phase 3's file list per §21.

- [ ] **Step 1: Create the component**

Create `src/components/IdentityGlyph.jsx`:

```jsx
import { memo } from 'react';
import { motion } from 'motion/react';
import './IdentityGlyph.css';

function hashString(str) {
  let hash = 0;
  for (let i = 0; i < str.length; i += 1) {
    hash = (hash * 31 + str.charCodeAt(i)) >>> 0;
  }
  return hash;
}

function IdentityGlyph({ projectId, layoutId, size = 28, className = '' }) {
  const hash = hashString(projectId);
  const cells = Array.from({ length: 25 }, (_, i) => (hash >> i) & 1);

  return (
    <motion.div
      layoutId={layoutId}
      className={`identity-glyph ${className}`}
      style={{ width: size, height: size }}
      aria-hidden="true"
    >
      {cells.map((filled, i) => (
        <span key={i} className={filled ? 'is-filled' : 'is-empty'} />
      ))}
    </motion.div>
  );
}

export default memo(IdentityGlyph);
```

(25 cells from a 5×5 grid, one bit of the hash per cell — deterministic: the same `projectId` always yields the same pattern, since `hashString` has no randomness and bit-extraction is pure.)

- [ ] **Step 1: Remove the AnimatePresence "wait" mode in App.jsx**

`src/App.jsx:57` currently reads:

```jsx
        <AnimatePresence mode="wait" initial={false}>
```

Change it to:

```jsx
        <AnimatePresence initial={false}>
```

Why: `mode="wait"` fully unmounts the outgoing route before mounting the incoming one — the two never coexist in the DOM, so a `layoutId`-matched element (Task 1's glyph) has nothing to animate between; the transition would just cut instantly with no visual connection. Removing `mode="wait"` (the default is `mode="sync"`, which lets outgoing and incoming routes overlap for the duration of their exit/enter animations) is the standard, documented way `motion/react` supports shared-layout transitions across route changes. Side effect, expected and fine: the current hard "old page fades out, THEN new page fades in" sequence becomes a proper overlapping crossfade — a visual improvement, not a regression.

- [ ] **Step 3: Text-scramble the title, blur-resolve the body paragraphs**

Add above the `ProjectDetail` function:

```jsx
const SCRAMBLE_CHARS = 'ABCDEFGHIJKLMNOPQRSTUVWXYZ01#$%';

function useScrambleReveal(text) {
  const [display, setDisplay] = useState(text);

  useEffect(() => {
    let frame = 0;
    const totalFrames = 18;
    const intervalId = window.setInterval(() => {
      frame += 1;
      const revealCount = Math.floor((frame / totalFrames) * text.length);
      const scrambled = text
        .split('')
        .map((char, i) => {
          if (char === ' ') return ' ';
          if (i < revealCount) return char;
          return SCRAMBLE_CHARS[Math.floor(Math.random() * SCRAMBLE_CHARS.length)];
        })
        .join('');
      setDisplay(scrambled);
      if (frame >= totalFrames) window.clearInterval(intervalId);
    }, 40);

    return () => window.clearInterval(intervalId);
  }, [text]);

  return display;
}

function ResolveParagraph({ text, className }) {
  return (
    <motion.p
      className={className}
      initial={{ opacity: 0, filter: 'blur(6px)' }}
      whileInView={{ opacity: 1, filter: 'blur(0px)' }}
      viewport={{ once: true, margin: '-10%' }}
      transition={{ duration: 0.6, ease: [0.4, 0, 0.2, 1] }}
    >
      {text}
    </motion.p>
  );
}
```
